Архітектура системи, доменна модель, AI-підсистема та інженерні рішення — від того, що вже працює, до того, що спроєктовано на масштаб.

01Про документ

Це технічна специфікація проєкту AI Loadboard — вантажної біржі з прямим з'єднанням вантажовідправника і перевізника, без брокера-посередника. На відміну від інвесторського огляду (project-documentation.html), тут немає маркетингового спрощення: документ описує систему так, як її бачить інженерна команда — включно з тим, що ще не побудовано.

Аудиторія: технічні співзасновники, майбутні інженери, що приєднуються до команди, і технічний due diligence з боку інвестора.

Кожен розділ і кожен рядок таблиці позначені міткою зрілості:

MVP · готово — реалізовано і працює в поточному демо-каркасі· Фаза 2 — у найближчому спринті розробки· Фаза 3 — заплановано, дизайн ще не заморожений· R&D — потребує дослідження/прототипування моделі перед комітом у продукт· Ризик — відомий технічний борг або відкрите питання.

Документ навмисно не приховує незрілість поточної кодової бази: MVP — це навмисно спрощений транзакційний каркас (реєстрація → публікація вантажу → взяття вантажу → завершення), без жодної AI-функції, зібраний, щоб перевірити базовий цикл shipper↔carrier до інвестиції в ML-шар.

02Огляд системи та рівень зрілості

AI Loadboard — двостороння платформа: вантажовідправник публікує вантаж, перевізник бачить його і бере напряму, без брокера. Довгострокове бачення — не лише дошка оголошень, а система, де AI виконує роботу диспетчера й брокера: підбирає вантаж, прогнозує ставку, веде перші переговори, перевіряє контрагента і обробляє документи.

03Архітектура верхнього рівня

Система розділена на дві половини з різними вимогами до надійності й латентності. Core Loadboard Service — транзакційне ядро (реєстрація, вантажі, статуси, платежі в майбутньому): має бути швидким, консистентним, з жорсткими SLA. AI-сервіси — обчислювально важкі, залежать від зовнішніх LLM/ML-провайдерів, можуть відповідати з затримкою в секунди і не повинні блокувати транзакційний шлях. Тому вони зв'язані асинхронно через шину подій, а не прямими синхронними викликами.

Наразі реалізований лише прямокутник Core Loadboard Service ↔ PostgreSQL у верхній половині схеми — без API Gateway, без шини подій, без жодного AI-сервіса. Решта — цільова архітектура, під яку вже зараз проєктується доменна модель (розділ 5) і контракти подій.

Чому шина подій, а не прямі виклики

  • Ізоляція збоїв. Якщо LLM-провайдер деградує чи впав, публікація вантажу і взяття вантажу продовжують працювати — це різні відмовостійкі домени.
  • Незалежне масштабування й деплой. Negotiation Agent можна викотити окремо від Core, дати йому свій пул воркерів і GPU/API-бюджет, не чіпаючи транзакційний код.
  • Заміна моделі без даунтайму ядра. Провайдер LLM або алгоритм скорингу можна змінити, підключивши нову версію споживача до тієї самої події.
  • Аудит за замовчуванням. Кожна подія — це запис у журналі: хто що запропонував і коли, важливо для спорів «AI щось пообіцяв контрагенту».

05Доменна модель даних

Поточна схема — дві таблиці, свідомо мінімальні для MVP:

-- backend/app/models.py — те, що реально існує сьогодні

users(id, email UNIQUE, hashed_password, company_name,
      role ENUM(shipper|carrier), created_at)

loads(id, title, origin, destination, equipment_type DEFAULT 'Dry Van',
      weight_lbs, price_usd NUMERIC(10,2),
      shipper_id FK→users NULLABLE, carrier_id FK→users NULLABLE,
      shipper_name, carrier_name NULLABLE,
      status ENUM(open|accepted|completed), created_at, accepted_at NULLABLE)
Вирішено (достроково, ще у Фазі MVP): loads тепер має shipper_id/carrier_id як FK на users — вантаж пов'язаний з автентифікованим користувачем, який його опублікував чи взяв, і саме на це посилання спираються перевірки власності на рівні API (розділ 8). shipper_name/carrier_name лишаються — це денормалізований кеш для відображення, тепер завжди встановлюється сервером із company_name власника, а не клієнтом. Було P0 у розділі 17, тепер закрито.

accepted_at (nullable, встановлюється сервером у accept_load) додано для ETA MVP (розділ 7.7) — це єдина точка відліку "початку рейсу", яку сьогодні має система, за відсутності телематики чи GPS перевізника.

Цільова схема (Фаза 2–3)

Розширення додає компанії (для trust-скорингу й MC/DOT-номерів), офери та історію переговорів, документи з результатами розпізнавання, знімки прогнозів ставки:

CREATE TABLE companies (
  id            BIGSERIAL PRIMARY KEY,
  legal_name    TEXT NOT NULL,
  mc_number     TEXT UNIQUE,      -- Motor Carrier number
  dot_number    TEXT UNIQUE,
  trust_score   NUMERIC(4,1),     -- кеш останнього скору, 0–100
  created_at    TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE offers (
  id            BIGSERIAL PRIMARY KEY,
  load_id       BIGINT REFERENCES loads(id),
  carrier_id    BIGINT REFERENCES users(id),
  price_usd     NUMERIC(10,2) NOT NULL,
  status        TEXT NOT NULL DEFAULT 'pending', -- pending|countered|accepted|rejected|expired
  source        TEXT NOT NULL DEFAULT 'human',   -- human|ai_agent
  created_at    TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE negotiation_messages (
  id              BIGSERIAL PRIMARY KEY,
  offer_id        BIGINT REFERENCES offers(id),
  sender          TEXT NOT NULL,   -- shipper|carrier|ai_agent
  channel         TEXT NOT NULL,   -- chat|email|sms|voice_transcript
  body            TEXT NOT NULL,
  proposed_price  NUMERIC(10,2),
  created_at      TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE trust_scores (
  company_id      BIGINT REFERENCES companies(id),
  score           NUMERIC(4,1) NOT NULL,   -- 0–100
  factors         JSONB NOT NULL,          -- {"payment_history":.., "insurance_valid":.., "doc_fraud_flags":..}
  model_version   TEXT NOT NULL,
  computed_at     TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (company_id, computed_at)
);

CREATE TABLE market_rate_snapshots (
  lane            TEXT NOT NULL,   -- напр. 'DAL-HOU'
  equipment_type  TEXT NOT NULL,
  predicted_at    TIMESTAMPTZ NOT NULL,
  horizon_days    INT NOT NULL,
  predicted_usd   NUMERIC(10,2) NOT NULL,
  confidence_low  NUMERIC(10,2),
  confidence_high NUMERIC(10,2),
  model_version   TEXT NOT NULL
);

CREATE TABLE documents (
  id              BIGSERIAL PRIMARY KEY,
  load_id         BIGINT REFERENCES loads(id),
  doc_type        TEXT NOT NULL,   -- bol|pod|rate_confirmation|insurance_coi
  storage_uri     TEXT NOT NULL,   -- s3://...
  extraction      JSONB,           -- структуровані поля з IDP-пайплайну
  confidence      NUMERIC(4,3),
  review_status   TEXT NOT NULL DEFAULT 'auto', -- auto|needs_review|reviewed
  created_at      TIMESTAMPTZ DEFAULT now()
);

loads.embedding vector(768) додається як колонка pgvector для семантичного пошуку й матчингу (розділ 7.3/7.6) — окрема векторна БД не потрібна, поки обсяг вантажів не вимагає ANN-індексів поза Postgres.

07AI/ML підсистема

Сім продуктових AI-функцій зі спільною інфраструктурою. Спільний принцип для всіх: модель ніколи не є єдиною точкою відмови — кожен сервіс має детерміністичний fallback (порожній список рекомендацій, останню відому ставку, ескалацію людині), і жоден AI-виклик не блокує основний транзакційний шлях (розділ 3).

7.1 AI-асистент переговорів

Найризикованіша функція продукту: модель веде реальну комунікацію від імені платформи і може «пообіцяти» ціну. Тому це єдиний AI-сервіс із жорстким контуром безпеки, а не просто LLM-викликом.

Чому саме так: LLM за конструкцією не гарантує дотримання числових меж лише інструкцією в промпті — тому перевірка меж винесена в детерміністичний код (check_bounds()), а не довірена моделі. Агент може пропонувати формулювання і тон, але не може обійти хардкоджену перевірку суми.

7.2 Автоматизація документообігу

Пайплайн розпізнавання BOL/POD/rate confirmation: upload → OCR/layout → LLM-структурування у JSON → перевірка впевненості → авто-збереження або черга ручної перевірки. Поле confidence з таблиці documents (розділ 5) — це мінімум confidence по обов'язкових полях (сума, дата, підпис/номер вантажу); нижче порогу (напр. 0.90) документ іде в чергу ручної перевірки замість автоматичного застосування. Кожне ручне виправлення записується як приклад для донавчання/промпт-тюнінгу — цикл зворотного зв'язку описаний у розділі 13.

7.3 Розумний підбір вантажу MVP

Реалізовано: GET /api/loads/matches (api/routes/matching.py) — детерміністична евристика, без LLM і без ML-моделі. Для перевізника з історією (будь-які вантажі, де він carrier_id, незалежно від статусу) кожен відкритий вантаж отримує бал: +3 за збіг типу кузова з раніше виконаними вантажами, +2 за збіг штату origin і +2 за збіг штату destination із лейнами перевізника; результат сортується за балом, потім за часом публікації. Перевізник без історії (новий акаунт) отримує звичайний список найновіших відкритих вантажів — той самий запит, що й GET /api/loads?status=open — це свідомий детермінований випадок ("холодний старт"), а не порожня чи зламана відповідь.

Чому не embeddings + gradient boosting одразу: цільова модель нижче потребує реальних поведінкових даних (історія прийнять/відмов у масштабі), яких у демо немає — навчання на кількох сід-вантажах дало б випадковий шум, а не сигнал. Той самий принцип, що й у NL Search (розділ 7.6): спершу детерміністична версія, що дає реальну користь сьогодні, апгрейд до моделі — коли з'являться дані, варті навчання.

7.4–7.7 Інші AI-сервіси — принципи проєктування

Matching — цільова модель (7.3)

Ембединги вантажу (маршрут, тип кузова, вага, час) + профіль перевізника (домашня база, вподобані лейни, історія прийнять/відмов) → cosine-подібність як базовий сигнал, gradient boosting поверх — для калібрування під фактичну конверсію в прийняття. Замінить евристику вище, коли зберуться реальні дані.

Pricing (7.4)

Прогноз на лейн-рівні (origin-dest-equipment), горизонт 1–7 днів, з довірчим інтервалом, а не точковим числом — платформа явно показує невпевненість, а не видає її за факт.

Trust Scoring (7.5)

0–100 з поясненими факторами (JSONB factors), не «чорна скринька» — перевізник/shipper бачить, чому скор такий, і може оскаржити. Низький скор не банить автоматично, а знижує пріоритет у матчингу і додає попередження.

NL Search (7.6) MVP

Реалізовано: POST /api/search (core/llm.py) шле запит у Claude Haiku 4.5 через messages.parse() зі структурованим виходом (SearchFilter: origin/destination/equipment_type/price_max/weight_min/weight_max), результат застосовується як звичайні SQLAlchemy-фільтри поверх loads. Векторний пошук за смисловою близькістю (embeddings) — ще не реалізовано, лишається ціллю Фази 2/3. Сам виклик до LLM вимкнений за замовчуванням прапорцем NL_SEARCH_ENABLED=false у .env — щоб не витрачати кредити Anthropic, поки хтось свідомо не увімкне; core/llm.py перевіряє цей прапорець ще до звернення до ключа. Якщо прапорець вимкнено, ключ ANTHROPIC_API_KEY відсутній, виклик до Anthropic падає або на акаунті скінчились кредити — фолбек не «форма з фільтрами» і не нефільтрований список, а простий пошук за ключовими словами (_keyword_filter): кожне слово запиту через ILIKE має збігтися хоч в одній із колонок title/origin/destination/equipment_type; ендпоінт ніколи не повертає помилку через відмову LLM і завжди хоч якось фільтрує.

ETA (7.7) MVP

Реалізовано: GET /api/loads/{id}/eta (core/eta.py) — детерміністична евристика, без ML-моделі. Геокодує origin/destination через Nominatim, отримує реальну відстань і тривалість руху через OSRM (ті самі провайдери, що й карта на фронтенді, тут викликаються з бекенда), і розширює звичайну (легковою) тривалість OSRM у діапазон [drive_hours_min, drive_hours_max] (×1.3) — наближення для типових обов'язкових зупинок на відпочинок під час далекого рейсу. Коли перевізник бере вантаж (loads.accepted_at, встановлюється сервером у accept_load), ендпоінт додає цей діапазон до accepted_at і повертає вікно прибуття (eta_earliest/eta_latest); до прийняття — лише оцінку часу в дорозі, бо немає точки відліку відправлення. На сторінці деталей вантажу відображається як панель «Estimated arrival» після прийняття вантажу.

Чому не справжня модель одразу: цільова модель потребує GPS-телематики перевізника, живого трафіку й погоди — нічого з цього в демо немає. Той самий принцип, що й у Matching (7.3) та NL Search (7.6): спершу детерміністична версія, що дає реальну користь сьогодні.

Спільне для всіх

Кожна модель має версію (model_version), логується вхід/вихід для офлайн-оцінки, і має задокументований fallback на детермінізм при відмові.

7.8 Спільна AI-інфраструктура

  • LLM Gateway — єдина точка виклику моделей: абстрагує провайдера (можливість перемкнутись між моделями без зміни коду сервісів), рахує вартість токенів на запит, застосовує тайм-аути й fallback на меншу/дешевшу модель при відмові основного провайдера.
  • Редагування PII перед відправкою назовні. Персональні дані водія/контактні дані контрагента маскуються перед тим, як текст іде до стороннього LLM-провайдера, і відновлюються після відповіді — вимога для документообігу з ПІБ водіїв і номерами телефонів.
  • Реєстр промптів і eval-набори. Кожен промпт версіонується; зміна промпту прогонюється проти зафіксованого набору реальних кейсів (regression suite для AI, а не лише для коду) перед викаткою.
  • Canary rollout моделей. Нова версія моделі/промпту спершу отримує невелику частку трафіку, порівнюється за метриками якості й вартості, і лише потім масштабується на 100%.
  • Бюджет вартості й circuit breaker. Ліміт витрат на AI-виклики за період; при перевищенні — деградація до дешевших/детерміністичних шляхів, а не мовчазне зростання рахунку.
  • Feature Store. Спільні ознаки (історія лейну, поведінка перевізника) обчислюються один раз і перевикористовуються Matching, Pricing і Trust сервісами замість дублювання логіки.

09Автентифікація, авторизація й ролі

Сьогодні: email+пароль → bcrypt-хеш → короткоживучий access-JWT (HS256, sub=email, 15 хв за замовчуванням) з python-jose + окремий refresh-токен (опаковий випадковий рядок, зберігається в БД лише як SHA-256-хеш, таблиця refresh_tokens). Ротація на кожному використанні (POST /api/auth/refresh) — старий refresh-токен помирає в момент видачі нового, тож повторне використання вкраденого токена після того, як легітимний клієнт уже зробив refresh, — відхилене повторне використання, а не тиха друга сесія. POST /api/auth/logout відкликає токен явно. Сам access-JWT відкликати не можна (він статичний за конструкцією), але коротке 15-хвилинне вікно замість 7 днів суттєво звужує вікно ризику. Фронтенд оновлює access-токен у фоні непомітно для користувача (AuthContext.tsx). Обидва токени зберігаються в localStorage — це усвідомлений компроміс, не цільовий дизайн (див. нижче).

13Спостережуваність

Сьогодні — лише stdout-логи uvicorn, нічого структурованого. Цільовий стек:

  • Логи — структуровані (JSON), з request_id, що проходить через Gateway → Core → подію → AI-сервіс, для наскрізного трасування одного запиту користувача.
  • Метрики — Prometheus: латентність по ендпоінтах, довжина черги подій, вартість AI-викликів у доларах на добу.
  • Трейсинг — OpenTelemetry, окремо позначені AI-спани (модель, кількість токенів, латентність провайдера).
  • AI-специфічна спостережуваність: eval-пайплайн на semplе реальних кейсів після кожної зміни промпту/моделі; дрейф якості (частка ескалацій Negotiation Agent людині — раптове зростання сигналізує про регресію); черга людського review для документів і скорингу як явний UI, а не побічний ефект.
  • Цикл зворотного зв'язку. Кожне ручне виправлення (диспетчер поправив офер AI, людина виправила поле документа) записується як приклад для наступного eval-набору й потенційного донавчання/промпт-тюнінгу.

01About this document

This is the technical specification for AI Loadboard — a freight marketplace that connects shippers and carriers directly, with no broker in between. Unlike the investor overview (project-documentation.html), there's no marketing simplification here: the document describes the system the way the engineering team sees it — including what hasn't been built yet.

Audience: technical co-founders, future engineers joining the team, and investor-side technical due diligence.

Every section and every table row carries a maturity label:

MVP · done — implemented and running in the current demo scaffold· Phase 2 — next up in the development sprint· Phase 3 — planned, design not yet frozen· R&D — needs research/prototyping before it's committed to the product· Risk — known technical debt or an open question.

The document deliberately doesn't hide the immaturity of the current codebase: the MVP is an intentionally minimal transactional scaffold (sign up → post a load → take a load → complete it), with zero AI features, built to validate the core shipper↔carrier loop before investing in the ML layer.

02Overview & maturity

AI Loadboard is a two-sided platform: a shipper posts a load, a carrier sees it and takes it directly — no broker. The long-term vision isn't just a bulletin board — it's a system where AI does the work of a dispatcher and a broker: matching loads, forecasting rates, running the first round of negotiation, vetting counterparties, and processing documents.

03Top-level architecture

The system splits into two halves with different reliability and latency requirements. The Core Loadboard Service is the transactional core (accounts, loads, statuses, payments down the line): it has to be fast, consistent, and held to strict SLAs. The AI services are compute-heavy, depend on external LLM/ML providers, may take seconds to respond, and must never block the transactional path. That's why they're connected asynchronously through an event bus rather than direct synchronous calls.

Right now only the rectangle Core Loadboard Service ↔ PostgreSQL in the top half of the diagram is actually built — no API Gateway, no event bus, no AI service at all. Everything else is the target architecture the data model (section 5) and event contracts are already being designed around.

Why an event bus instead of direct calls

  • Failure isolation. If an LLM provider degrades or goes down, posting and taking loads keep working — they're separate failure domains.
  • Independent scaling and deploys. The Negotiation Agent can ship separately from Core, with its own worker pool and GPU/API budget, without touching transactional code.
  • Swapping models without core downtime. An LLM provider or scoring algorithm can be changed by pointing a new consumer version at the same event.
  • Audit by default. Every event is a journal entry — who proposed what and when — which matters for disputes over what the AI "promised" a counterparty.

Seven product-facing AI features on shared infrastructure. 7.1 AI negotiation assistant

The product's riskiest feature: the model conducts real communication on the platform's behalf and can effectively "promise" a price. That's why it's the only AI service with a hard safety perimeter, not just an LLM call.

Why it works this way: an LLM, by construction, doesn't guarantee it will respect numeric bounds just because a prompt tells it to — so bound-checking is pulled out into deterministic code (check_bounds()) rather than trusted to the model. The agent can shape wording and tone, but it can't get around the hardcoded amount check.

7.2 Document automation

The recognition pipeline for BOL/POD/rate confirmation: upload → OCR/layout → LLM structuring into JSON → confidence check → auto-file or manual-review queue. The confidence field on the documents table (section 5) is the minimum confidence across required fields (amount, date, signature/load number); below the threshold (e.g. 0.90) the document goes into the manual-review queue instead of being applied automatically. Every manual correction is logged as a training example for fine-tuning/prompt tuning — the feedback loop is described in section 13.

7.3 Smart load matching MVP

Shipped: GET /api/loads/matches (api/routes/matching.py) — a deterministic heuristic, no LLM and no ML model. For a carrier with history (any load where they're the carrier_id, any status), every open load gets a score: +3 for an equipment type they've hauled before, +2 for an origin-state match, +2 for a destination-state match against the carrier's own lanes; results sort by score, then by post time. A carrier with no history yet (a fresh account) gets the plain newest-first open list — the same query GET /api/loads?status=open runs — a deliberate deterministic "cold start" case, not an empty or broken response.

Why not embeddings + gradient boosting yet: the target model below needs real behavioral data (accept/decline history at scale) that doesn't exist in a demo — training on a handful of seed loads would learn noise, not signal. Same principle as NL Search (section 7.6): ship the deterministic version that's actually useful today, upgrade to a model once there's data worth learning from.

7.4–7.7 Other AI services — design principles

Matching — target model (7.3)

Load embeddings (route, equipment type, weight, timing) + carrier profile (home base, preferred lanes, accept/decline history) → cosine similarity as the base signal, with gradient boosting on top to calibrate against actual acceptance conversion. Replaces the heuristic above once real data accumulates.

Pricing (7.4)

Forecast at the lane level (origin-dest-equipment), 1–7 day horizon, with a confidence interval rather than a point number — the platform shows its uncertainty explicitly instead of passing it off as fact.

Trust Scoring (7.5)

0–100 with explained factors (JSONB factors), not a black box — the carrier/shipper can see why the score is what it is, and can dispute it. A low score doesn't auto-ban; it lowers matching priority and adds a warning.

NL Search (7.6) MVP

Shipped: POST /api/search (core/llm.py) calls Claude Haiku 4.5 via messages.parse() with a structured output (SearchFilter: origin/destination/equipment_type/price_max/weight_min/weight_max), and the result is applied as ordinary SQLAlchemy filters over loads. Vector search by semantic closeness (embeddings) isn't built yet — still a Phase 2/3 target. The LLM call itself is off by default behind a NL_SEARCH_ENABLED=false flag in .env — so it never spends Anthropic credits until someone deliberately turns it on; core/llm.py checks the flag before it even looks at the key. If the flag is off, ANTHROPIC_API_KEY is missing, the Anthropic call fails, or the account is out of credit, the fallback is neither a "filter form" nor the unfiltered list — it's a plain keyword match (_keyword_filter): every word in the query must ILIKE-match at least one of title/origin/destination/equipment_type; the endpoint never errors out on an LLM failure and always filters something.

ETA (7.7) MVP

Shipped: GET /api/loads/{id}/eta (core/eta.py) — a deterministic heuristic, no ML model. Geocodes origin/destination via Nominatim, fetches the real driving distance/duration via OSRM (same providers as the frontend's map, called server-side here), and widens OSRM's plain car-profile duration into a [drive_hours_min, drive_hours_max] band (×1.3) — a stand-in for typical mandatory rest stops on a long haul. Once a carrier accepts a load (loads.accepted_at, set server-side by accept_load), the endpoint adds that band to accepted_at and returns an arrival window (eta_earliest/eta_latest); before acceptance it returns the transit-time estimate only, since there's no departure time to anchor a window to. Surfaced on the load detail page as an "Estimated arrival" panel once a load is accepted.

Why not the real model yet: the target model needs carrier GPS telematics, live traffic, and weather — none of which exist in this demo. Same principle as Matching (7.3) and NL Search (7.6): ship the deterministic version that's actually useful today.

Common to all

Every model carries a version (model_version), logs input/output for offline evaluation, and has a documented fallback to deterministic behavior on failure.

7.8 Shared AI infrastructure

  • LLM Gateway — a single call point for models: abstracts the provider (swap models without changing service code), meters token cost per request, applies timeouts, and falls back to a smaller/cheaper model if the primary provider fails.
  • PII redaction before outbound calls. Driver personal data and counterparty contact details are masked before the text goes to a third-party LLM provider, and restored after the response — a requirement for document flows carrying driver names and phone numbers.
  • Prompt registry and eval sets. Every prompt is versioned; a prompt change is run against a fixed set of real cases (a regression suite for AI, not just for code) before it ships.
  • Canary model rollout. A new model/prompt version first gets a small slice of traffic, is compared on quality and cost metrics, and only then is scaled to 100%.
  • Cost budget and circuit breaker. A spend cap on AI calls per period; going over it degrades to cheaper/deterministic paths instead of silently running up the bill.
  • Feature Store. Shared features (lane history, carrier behavior) are computed once and reused by Matching, Pricing, and Trust instead of duplicating the logic.

09Authentication, authorization & roles

Today: email+password → bcrypt hash → a short-lived access JWT (HS256, sub=email, 15 min by default) via python-jose plus a separate refresh token (an opaque random string, stored in the DB only as a SHA-256 hash, refresh_tokens table). It rotates on every use (POST /api/auth/refresh) — the old refresh token dies the instant a new one is issued, so a stolen token that gets replayed after the legitimate client has already refreshed is a rejected reuse, not a silent second session. POST /api/auth/logout revokes it outright. The access JWT itself still can't be revoked (stateless by design), but the 15-minute window bounds the blast radius far more than 7 days did. The frontend refreshes the access token in the background, invisibly to the user (AuthContext.tsx). Both tokens live in localStorage — a deliberate simplification, not the target design (see below).

12Performance & scalability

  • Caching. Redis for the "hot" list of open loads and rate-forecast results (a few minutes' TTL — a forecast shouldn't be recomputed on every list render).
  • Async work. Heavy AI calls (negotiation, OCR) run through a queue (Celery/RQ on Redis, later Kafka), not inside the API's request-response cycle.

  • Read replicas. Load-list and analytics reads come from a replica; writes stay on primary — once load justifies it.
  • CDN. Frontend static assets and uploaded documents (via signed URLs) sit behind a CDN, not proxied through the backend.

13Observability

Today — just uvicorn's stdout logs, nothing structured. The target stack:

  • Logs — structured (JSON), carrying a request_id through Gateway → Core → event → AI service, for end-to-end tracing of a single user request.
  • Metrics — Prometheus: per-endpoint latency, event-queue depth, AI call cost in dollars per day.
  • Tracing — OpenTelemetry, with AI spans tagged separately (model, token count, provider latency).
  • AI-specific observability: an eval pipeline against real cases after every prompt/model change; quality drift (a sudden jump in the Negotiation Agent's human-escalation rate signals a regression); a human review queue for documents and scoring as an explicit UI, not a side effect.
  • Feedback loop. Every manual correction (a dispatcher fixing an AI offer, a human correcting a document field) is logged as a training example for the next eval set and potential fine-tuning/prompt tuning.
